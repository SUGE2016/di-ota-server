# OTA 架构改进方案 v2

**日期:** 2026-06-05  
**状态:** 已评审通过，待分阶段实施  
**前置文档:** `第三方OTA服务接入架构Proposal.md`、`技术方案.md`  
**变更说明:** 在保留「C 直连 O 完成下载与上报、O 为升级决策权威」前提下，**允许 B↔O 受控集成**，替代纯 CSV 人肉同步；B 通过 hint 缩短发现延迟，不代理大包、不裁决升级。

---

## 1. 目标

1. **O 域闭环**：注册表校验、任务快照、版本策略、可解释拒绝、Success 回写。
2. **B↔O 受控集成**：批量目录同步 + 待升级清单；可选 webhook。
3. **C 双通道**：B 心跳（业务 + `ota_hint`）+ O 权威链路（check / download / report）。
4. **可降级**：集成 API 不可用时，CSV 导入 + C 直 poll O 仍可用。

---

## 2. 总体架构

```text
                         ┌──────────────────────────────────────┐
                         │              ota-server O             │
                         │ Registry │ Task+Snapshot │ Policy │ CDN │
                         └────▲──────────────▲───────────────────┘
                              │              │
                   ① catalog/sync          │ ③ check-update
                   ② pending-upgrades      │    download
                   (service token)          │    report-status
                              │              │
                      ┌───────┴──────┐       │
                      │  backend B   │       │
                      │ 设备主数据   │       │
                      └───────▲──────┘       │
                              │              │
                       ② 心跳 + ota_hint     │
                              │              │
                           设备 C ───────────┘

  ④ (可选) O ──webhook──► B   升级状态摘要
```

### 2.1 职责边界（修订）

| 能力 | B | O |
| --- | --- | --- |
| 设备主数据（权威） | ✓ | 影子注册表（同步副本） |
| 升级决策 | ✗ | ✓（唯一权威） |
| 固件下载 | ✗ | ✓（CDN URL） |
| 升级统计/审计 | ✗ | ✓ |
| 业务心跳/在线 | ✓ | ✗ |
| 目录同步 | 推送方 | 接收方 |
| 升级 hint | 转发缓存 | 生成清单 |
| 当前版本（业务视图） | C 心跳写入 | Success 回写注册表 |

## 3. 分阶段实施

| 阶段 | 范围 | 交付物 |
| --- | --- | --- |
| **P0** | O 内核 | 注册表校验、任务快照、版本策略、拒绝码、Success 回写 |

## 4. P0：O 内核改进

### 4.1 数据模型

#### 4.1.1 `t_device` 扩展

```sql
ALTER TABLE t_device ADD COLUMN IF NOT EXISTS reported_version VARCHAR(64) NOT NULL DEFAULT '';
ALTER TABLE t_device ADD COLUMN IF NOT EXISTS catalog_version VARCHAR(64) NOT NULL DEFAULT '';
ALTER TABLE t_device ADD COLUMN IF NOT EXISTS last_seen_at TIMESTAMPTZ;
ALTER TABLE t_device ADD COLUMN IF NOT EXISTS eligibility_state VARCHAR(32) NOT NULL DEFAULT 'active';
-- eligibility_state: active | blocked
```

| 字段 | 含义 |
| --- | --- |
| `reported_version` | C 在 check-update / Success 后 O 维护的版本（**升级决策优先**） |
| `catalog_version` | 最近一次 B→O 或 CSV 同步带入的版本（**B 视图**） |
| `last_seen_at` | 最后一次设备 API 访问 |
| `eligibility_state` | `blocked` 时拒绝升级 |
| `catalog_synced_at` | 最近一次目录同步时间 |
| `catalog_source` | 最近同步来源：`backend` \| `csv` |
| `inconsistency_flags` | JSON 数组，记录未消掉的冲突标记（见 §5.5） |

**版本字段分工（重要）：**

```text
catalog_version  ← B sync / CSV（业务侧认知，可滞后、可错误）
reported_version ← C→O 设备上报（O 侧设备真值，用于 check-update 策略）
```

`t_device.current_version` 保留兼容只读别名时指向 `reported_version`，新代码优先读写分列字段。

#### 4.1.2 `t_package` 扩展

```sql
ALTER TABLE t_package ADD COLUMN IF NOT EXISTS min_upgradable_version VARCHAR(64) NOT NULL DEFAULT '';
ALTER TABLE t_package ADD COLUMN IF NOT EXISTS force_upgrade BOOLEAN NOT NULL DEFAULT FALSE;
```

#### 4.1.3 任务目标快照 `t_task_target`

```sql
CREATE TABLE IF NOT EXISTS t_task_target (
  task_id VARCHAR(64) NOT NULL REFERENCES t_release_task(task_id),
  device_id VARCHAR(64) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (task_id, device_id)
);
CREATE INDEX IF NOT EXISTS idx_task_target_device ON t_task_target(device_id);
```

创建 Running 任务时，按规则从 `t_device` 生成快照写入 `t_task_target`。

#### 4.1.4 目录同步审计 `t_catalog_sync_batch`

```sql
CREATE TABLE IF NOT EXISTS t_catalog_sync_batch (
  batch_id VARCHAR(64) PRIMARY KEY,
  source VARCHAR(32) NOT NULL,  -- api | csv | s3
  mode VARCHAR(32) NOT NULL,    -- upsert | full_replace
  accepted_count INT NOT NULL DEFAULT 0,
  rejected_count INT NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 4.2 check-update 决策流程（修订）

```text
1. 设备鉴权（Bearer / 后续 HMAC）
2. 查 t_device by device_id
   - 不存在 → 2003 not_in_catalog
   - eligibility_state=blocked → 2004 device_blocked
   - group/model/hw 与注册表不一致 → 2006 identity_mismatch
3. 查 Running 任务：device_id ∈ t_task_target
4. schedule_time / 时间窗 / 黑名单（后续）
5. canary(device_id, task_id)
6. 版本策略：reported vs min_upgradable / target
   - 已 >= target → 2001 already_latest
   - < min_upgradable → 2007 version_not_eligible
7. 返回 package + download_url + task_id
8. 更新 last_seen_at；合并 current_version 到 reported_version（请求带入）
```

### 4.3 check-update 响应（修订）

**有升级 `code=0`：** 保持现有字段，增加：

```json
{
  "retry_after_sec": 86400
}
```

**无升级 `code=2001`：**

```json
{
  "code": 2001,
  "message": "No available upgrade",
  "data": {
    "has_update": false,
    "reason": "not_in_canary",
    "retry_after_sec": 3600
  }
}
```

**`reason` 枚举：**

| reason | 含义 |
| --- | --- |
| `no_running_task` | 无 Running 任务或未命中快照 |
| `not_in_canary` | 未命中灰度 |
| `already_latest` | 版本已满足 |
| `version_not_eligible` | 低于最小可升版本 |
| `not_in_catalog` | 未在注册表（也可用 code 2003） |
| `device_blocked` | 设备被禁用 |
| `identity_mismatch` | 请求参数与注册表不一致 |

**新增业务错误码：**

| code | HTTP | 含义 |
| --- | --- | --- |
| 2003 | 403 | not_in_catalog |
| 2004 | 403 | device_blocked |
| 2006 | 409 | identity_mismatch |
| 2007 | 200 | version_not_eligible（has_update=false） |

### 4.4 report-status 修订

- `status=Success` 时：`UPDATE t_device SET reported_version = target_version, last_seen_at = NOW()`
- 保持现有状态机与幂等

### 4.5 多任务冲突规则

多个 Running 任务命中同一 `device_id` 时：

1. `force_upgrade=true` 优先  
2. `created_at` 较新优先  
3. 仍冲突则返回 `task_id` 字典序较小者（实现简单、可测）

## 5. P1：B→O 目录同步 API

### 5.1 认证

- **Service Token**：`Authorization: Bearer <INTEGRATION_SERVICE_TOKEN>`
- 环境变量：`INTEGRATION_ENABLED=true`、`INTEGRATION_SERVICE_TOKEN=<secret>`
- 与设备 token、管理端 JWT 分离
- 建议 B 侧 IP  allowlist（部署层）

### 5.2 `POST /api/v1/integrations/catalog/sync`

**Headers：**

```http
Authorization: Bearer <service-token>
Content-Type: application/json
Idempotency-Key: <batch_id>
```

**Request：**

```json
{
  "batch_id": "20260605-org1001-001",
  "mode": "upsert",
  "source": "backend",
  "sync_options": {
    "version_policy": "preserve_device_reported",
    "on_identity_change": "require_force_flag",
    "stale_batch_before": "2026-06-05T08:00:00Z"
  },
  "devices": [
    {
      "device_id": "AMS000001",
      "product_code": "AMS",
      "product_model": "V9",
      "hardware_version": "1.0",
      "current_version": "v2.3.0",
      "device_group": "org-1001",
      "tags": { "batch": "2026-05" }
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `batch_id` | ✓ | 全局唯一，幂等 |
| `mode` | ✓ | `upsert` \| `full_replace` |
| `source` | | 默认 `backend` |
| `devices` | ✓ | 单批最多 5000 条（可配置） |
| `sync_options.version_policy` | | 见 §5.5，默认 `preserve_device_reported` |
| `sync_options.on_identity_change` | | 见 §5.5，默认 `require_force_flag` |
| `sync_options.stale_batch_before` | | 可选，拒绝早于该时间的 B 侧批次（防乱序重放） |

设备行级可选字段：

| 字段 | 说明 |
| --- | --- |
| `force_identity_update` | `true` 时允许覆盖 model/hw/group（需 `on_identity_change=require_force_flag`） |
| `force_catalog_version` | `true` 时允许用 B 版本覆盖 `reported_version`（需 `version_policy=trust_catalog` 或行级强制） |

**`full_replace` 语义：** 本批未出现的 `device_id` 不自动删除；全量替换需显式传 `scope.device_group`（后续扩展），首期仅 `upsert`。

**Response `200`：**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "batch_id": "20260605-org1001-001",
    "accepted": 1198,
    "warned": 2,
    "rejected": 2,
    "warning_rows": [
      {
        "device_id": "AMS000001",
        "code": "version_rollback_ignored",
        "message": "catalog v2.1.0 is lower than reported v2.4.0; catalog_version updated, reported_version preserved",
        "catalog_version": "v2.1.0",
        "reported_version": "v2.4.0"
      }
    ],
    "rejected_rows": [
      { "index": 3, "device_id": "", "code": "invalid_field", "message": "device_id is required" },
      {
        "index": 9,
        "device_id": "AMS000009",
        "code": "identity_change_rejected",
        "message": "product_model changed V9->V10; set force_identity_update=true to apply"
      }
    ]
  }
}
```

**`warning_rows.code` 枚举：**

| code | 含义 | 默认处理 |
| --- | --- | --- |
| `version_rollback_ignored` | B 版本低于 O 的 `reported_version` | 更新 `catalog_version`，**不**降低 `reported_version` |
| `version_ahead_of_device` | B 版本高于 `reported_version` | 更新 `catalog_version`；`reported_version` 仍等 C 确认 |
| `version_parse_failed` | 版本号无法比较 | 按字符串存 `catalog_version`，打 flag，管理台可见 |
| `identity_changed` | group/tags 变更 | 默认允许并审计；Running 任务快照不变 |
| `identity_change_applied` | model/hw 变更且已 force | 更新注册表，打 flag |
| `stale_device_record` | 行内 `updated_at` 早于 O 已有同步 | 跳过该行，见 §5.5.4 |

**`rejected_rows.code` 枚举：**

| code | 含义 |
| --- | --- |
| `invalid_field` | 缺必填、超长等 |
| `identity_change_rejected` | model/hw 变更未带 force |
| `device_blocked` | 设备在 O 侧被 block，拒绝覆盖 |
| `batch_out_of_order` | 整批 `stale_batch_before` 校验失败 |

**错误（HTTP 层）：**

| code | 说明 |
| --- | --- |
| 1001 | 未授权 |
| 1002 | 参数错误 |
| 1003 | 重复 batch_id（幂等：返回首次结果） |
| 5000 | 内部错误 |

### 5.3 B 侧调用约定

- **频率**：每 15～60 分钟增量；全量每日一次（低峰）
- **粒度**：按 `device_group` 或更新时间分批，单批 ≤ 5000
- **字段**：与 CSV 模板一致；**禁止** PII
- **失败**：指数退避重试；仍失败则降级 CSV 手工导入

### 5.4 与 CSV 关系

- CSV 导入保留，写入 `source=csv`
- 管理台展示最近 sync batch、`warning_rows` / `rejected_rows`
- CSV/API 写入 **`catalog_version`**，不直接覆盖 **`reported_version`**（规则同 §5.5）
- 同一 `device_id` 多来源时：**以 `catalog_synced_at` 最新者为准** 更新 catalog 字段；冲突打 `inconsistency_flags`

### 5.5 版本倒退与数据不一致

#### 5.5.1 三类数据源与优先级

| 来源 | 字段 | 可信度（升级决策） | 典型延迟 |
| --- | --- | --- | --- |
| C→O check-update / report | `reported_version` | **最高** | 实时 |
| B→O catalog/sync | `catalog_version` | 中（筛选/运营参考） | 分钟～小时 |
| B 心跳（不直写 O） | 不写入 O | 仅 B 域 | - |

**check-update 版本策略默认只用 `reported_version`**（C 请求带入会刷新）。  
`catalog_version` 用于：管理台展示、pending-upgrades 预筛、**设备长期未上线时** 的降级参考（可选，默认关）。

#### 5.5.2 版本倒退（catalog 低于 reported）

**场景：** B 数据恢复、心跳滞后、导出错批次，sync 带来 `v2.1`，O 已有 `reported_version=v2.4`。

**默认策略 `preserve_device_reported`：**

```text
catalog_version  ← 更新为 B 传入值（记录 B 当前认知）
reported_version ← 保持不变
inconsistency_flags += version_rollback_ignored
响应 warning_rows
```

**不得**因 sync 单独降低 `reported_version`，否则会导致已对 Success 的设备再次下发旧包。

**纠正 O 侧版本真值的合法途径：**

1. C 再次 check-update / report-status 带真实 `current_version`
2. 管理端人工「重置 reported_version」（审计）
3. sync 行级 `force_catalog_version=true` 且 `version_policy=trust_catalog`（**仅运维纠错**）

#### 5.5.3 版本超前（catalog 高于 reported）

**场景：** B 已从心跳收到新版本，O 尚未收到 C 的 check-update。

```text
catalog_version  ← 更新
reported_version ← 暂不抬高（等设备确认）
```

check-update 以 **C 请求的 current_version** 为准做策略；B 虚高**不得**导致 `already_latest` 误拒。

#### 5.5.4 乱序与重复批次

| 机制 | 说明 |
| --- | --- |
| `batch_id` 幂等 | 同一 batch 重放返回相同结果 |
| `sync_options.stale_batch_before` | 拒绝整批旧导出 |
| 行级 `updated_at`（B 可选） | 早于 `catalog_synced_at` → `stale_device_record`，跳过 |
| `catalog_synced_at` | 每次成功 upsert 更新 |

#### 5.5.5 身份字段不一致

| 变更类型 | 默认策略 |
| --- | --- |
| `device_group` / `tags` | 允许 + 审计 |
| `product_code` | 允许 + warning |
| `product_model` / `hardware_version` | 拒绝，除非 `force_identity_update=true` |

身份变更**不修改**已冻结 `t_task_target`；新任务用新注册表。

#### 5.5.6 CSV 与 API 互斥写

新 sync 的 `catalog_synced_at` 更晚才覆盖 catalog 字段；否则 `stale_device_record`。  
`reported_version` 始终遵循 §5.5.2 / §5.5.3。

#### 5.5.7 管理台与审计

- 展示双版本 + `inconsistency_flags`
- sync 批次与逐行 warning 可检索

#### 5.5.8 决策表

| 条件 | 动作 |
| --- | --- |
| sync v < reported | catalog←v；reported 不变；warn rollback |
| sync v > reported | catalog←v；reported 不变；可选 warn ahead |
| force + trust_catalog | reported←v；审计 |
| model 变更无 force | reject |

## 6. P2：待升级清单 + B 心跳 hint

### 6.1 `GET /api/v1/integrations/pending-upgrades`

**Query：**

| 参数 | 说明 |
| --- | --- |
| `since` | 游标，首次省略 |
| `limit` | 默认 500，最大 2000 |
| `device_group` | 可选，按组过滤 |

**Response：**

```json
{
  "code": 0,
  "data": {
    "cursor": "eyJvZmZzZXQiOjUwMH0",
    "items": [
      {
        "device_id": "AMS000001",
        "task_id": "task-20260605-001",
        "target_version": "v2.4.0",
        "package_id": "pkg-xxx",
        "hint_expires_at": "2026-06-06T00:00:00Z"
      }
    ],
    "has_more": true
  }
}
```

**生成规则（O 侧 Worker，每 1～5 分钟）：**

- 遍历 Running 任务 + `t_task_target`
- 应用 canary + 版本策略（与 check-update 一致）
- 排除已成功 / 已 Failed 且不可重试的设备
- 写入 Redis 或物化视图 `t_pending_upgrade_hint`（实现可选）

**hint 有效期：** 默认 24h，过期后 B 缓存失效，C 仍可通过 poll O 发现升级。

### 6.2 B 心跳响应扩展

B **自行定义**心跳接口；O 只规范 **建议嵌入字段**：

```json
{
  "code": 0,
  "message": "ok",
  "ota_hint": {
    "need_upgrade": true,
    "task_id": "task-20260605-001",
    "target_version": "v2.4.0",
    "ota_base_url": "https://ota.example.com",
    "hint_expires_at": "2026-06-06T00:00:00Z"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `need_upgrade` | `false` 时可省略整个 `ota_hint` |
| `task_id` | C 在 check-update 时可作 hint（O 仍校验） |
| `ota_base_url` | C 配置的 O 地址，便于多环境 |

**B 侧逻辑：**

```text
loop 每 N 分钟:
  cursor = ""
  repeat:
    resp = GET O /integrations/pending-upgrades?since=cursor&device_group=...
    merge resp.items into local cache Map<device_id, hint>
    cursor = resp.cursor
  until not resp.has_more

on 心跳(sn):
  hint = cache.get(sn)
  if hint && now < hint_expires_at:
    回复 ota_hint
  else:
    不附带 ota_hint
```

### 6.3 C 侧行为（P3 SDK）

```text
on 收到 ota_hint.need_upgrade:
  schedule OTA check within 0~30min random jitter

on 定时器 / 周期性（如 12h）:
  O.checkUpdate()

on checkUpdate 成功 has_update:
  persist task_id
  download → verify → apply
  report-status 状态链
  B.heartbeat(new_version)
```

**原则：** hint 仅 **提前触发** check-update，**不跳过** O 校验与下载。

## 8. 降级策略

| 故障 | 行为 |
| --- | --- |
| B→O sync 失败 | B 重试；运营可 CSV 导入；O 用上次注册表 |
| pending-upgrades 不可用 | B 不附 hint；C 靠周期 poll O |
| O 不可用 | C 跳过 OTA；B 心跳正常 |
| hint 过期 / 错误 | C check-update 以 O 为准，忽略 hint |

---

## 9. 安全清单

| 项 | 要求 |
| --- | --- |
| B→O | Service Token + TLS + 可选 IP 限制 |
| C→O | 生产 `DEVICE_API_AUTH_ENABLED=true`；后续 HMAC |
| 下载 | CDN + 短 TTL 预签名 |
| Webhook | HMAC 签名校验 |
| 数据 | sync 不含 PII |
